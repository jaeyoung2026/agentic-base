# 설계 결정과 그 이유

> 이 문서는 "왜 이렇게 만들었는가"만 담는다. "무엇"과 "어떻게"는 AGENTS.md와 코드를 본다.

---

## 전제: 에이전트의 생산성은 코드베이스의 품질에 비례한다

에이전트를 잘 다루는 게 핵심이 아니다. **에이전트가 잘 일할 수 있는 코드베이스를 만드는 것**이 핵심이다.

LLM이 코드를 읽고 쓰는 환경에서:

- 패턴이 일관적이면 LLM이 같은 패턴으로 쓴다 — 품질이 전파된다
- 저품질 코드는 토큰을 낭비한다 — 코드 품질이 곧 비용 효율
- 코딩이 빨라지면서 병목이 코딩에서 **리뷰**로 이동했다
- 인간이 모든 코드를 리뷰할 수 없으므로, 통제감은 "게이트가 작동하는지 확인하는 것"으로 전환된다

---

## 1. Artifact 균일 인터페이스 — 왜 하나로 통일하는가

**결정:** 모든 산출물(대화, 문서, 검색 결과, 프로필, 카드)이 하나의 `Artifact` 인터페이스를 통과한다. 새 스토어와 새 영속 경로를 만들지 않는다.

**왜:**

- 데이터 경로가 하나면 LLM이 패턴을 학습하기 쉽다. 경로가 여러 개면 에이전트가 어느 경로로 저장할지 헷갈리고, 결국 새 경로를 또 만든다
- CRUD가 하나면 테스트, 권한, 감사 추적도 하나다. 곱셈이 아니라 덧셈이 된다
- lighthouse에서 실제로 겪은 문제: 검색 결과, 대화, 컬렉션이 각각 다른 경로를 갖자 에이전트가 우회 경로를 만들기 시작했다

**위반하면 생기는 일:** 새 타입을 추가할 때마다 별도 테이블, 별도 API, 별도 권한 체크가 필요해진다. 처음엔 빠르지만 3개째부터 복잡도가 폭발한다.

---

## 2. 3-Plane 분리 — 왜 Product/Agent/Execution인가

**결정:** `Product → Agent → Execution` 방향으로만 참조. 역방향 금지.

**왜:**

- **Product Plane**(UI)은 가장 자주 바뀐다. 여기가 Agent나 Execution을 직접 건드리면 UI 변경이 전체를 흔든다
- **Agent Plane**(정책)은 비즈니스 규칙이다. UI가 바뀌어도 정책은 유지되어야 한다
- **Execution Plane**(DB, 외부 API)은 인프라다. 프로바이더를 바꿔도 정책과 UI에 영향이 없어야 한다
- 역참조가 생기면 한 층의 변경이 다른 층을 깨뜨린다. dependency-cruiser가 이를 자동으로 잡는다

**실전 예시:** Supabase에서 다른 DB로 교체할 때, Execution만 바꾸면 된다. Agent와 Product는 건드리지 않는다.

---

## 3. PAR Loop — 왜 plan → execute → audit인가

**결정:** 매 턴마다 plan(무엇에 집중할지 결정) → execute(실행) → audit(판정) 파이프라인을 돈다.

**왜:**

- LLM은 **시스템 프롬프트에 있는 것만 지킨다**. 프롬프트에 없는 규칙은 무시한다
- plan이 매 턴 맥락을 읽고 "이번에 뭘 지켜야 하는지"를 결정해서 execute의 시스템 프롬프트에 주입한다
- execute만 있으면 "잘 되겠지" 하고 기도하는 것이다. audit이 있어야 "실제로 지켰는지" 판정하고 다음 턴에 반영한다
- 이 구조는 [Co-actor Standard](https://github.com/jaeyoungkang/mirror-mind)에서 나왔다. AI를 도구가 아니라 동료로 설계하기 위한 실행 표준

**위반하면 생기는 일:** 프롬프트가 길어지면 LLM이 뒷부분을 무시한다. plan 없이 모든 규칙을 프롬프트에 넣으면 컨텍스트 낭비 + 규칙 위반 증가.

## 4. 품질 게이트 8종 — 왜 이렇게 많은가

**결정:** Formatter, Linter, jscpd, Test coverage, knip, dependency-cruiser, tloc, specdown을 모두 강제한다.

**왜:** 에이전트가 만드는 코드에는 반복되는 약점이 있다:

| 약점                                           | 대응 게이트                           |
| ---------------------------------------------- | ------------------------------------- |
| 꼼수를 먼저 시도한다 (`eslint-disable`, `any`) | Linter + escape guard                 |
| 코드 삭제를 잘 하지 않는다                     | knip (죽은 코드 탐지)                 |
| 중복 코드를 만든다                             | jscpd (중복 탐지)                     |
| 중복 테스트를 과다 생성한다                    | tloc (테스트/프로덕션 비율 120% 이하) |
| Import 방향을 무시한다                         | dependency-cruiser                    |
| 스펙과 구현이 달라진다                         | specdown (실행 가능 스펙)             |

하나만 강제하면 다른 쪽이 터진다. **도구 조합**이 중요하다.

**핵심 원리:** 암묵적 경계를 명시적으로 만들고, 자동으로 강제한다. 사람끼리는 암묵적 합의가 통하지만, **에이전트는 암묵적 합의를 모른다**.

## 5. LLM 이원화 — 왜 plan과 execute를 분리하는가

**결정:** `structuredInference()`(구조화 출력)와 `streamExecution()`(스트리밍)을 분리한다.

**왜:**

- **Plan** = 판단. "이번 턴에 뭘 해야 하는가?" → 정답이 구조화된 JSON이다. 자유 텍스트가 아니다
- **Execute** = 실행. 사용자에게 응답 + 도구 사용 → 스트리밍이어야 사용자 경험이 좋다
- 같은 LLM 호출로 두 역할을 하면 판단과 실행이 섞여서 품질이 떨어진다
- 분리하면 plan만 더 정교한 모델로 바꾸거나, execute만 경량 모델로 바꾸는 독립적 최적화가 가능하다

---

## 6. 계산과 효과의 분리 — 왜 순수 함수를 강조하는가

**결정:** 정책 판단, 점수 계산, 프롬프트 조립, 응답 파싱은 순수 함수로. LLM 호출, DB 쿼리, 상태 변경은 가장자리에 격리.

**왜:**

- 순수 함수는 입력→출력이 예측 가능하다. LLM이 정확히 이해하고 안전하게 수정할 수 있다
- 순수 함수는 테스트가 쉽다. 테스트가 자동화된 리뷰어 역할을 한다
- 비순수 부분(LLM 호출, DB)이 코드 전체에 퍼지면 테스트도 어렵고 에이전트도 건드리기 무서워한다

**파일 배치:**

- `src/product/` = 순수한 비즈니스 로직 (테스트 가능)
- `src/execution/` = 비순수한 외부 연결 (격리)
- `src/agent/` = 순수한 판단 로직 + 비순수한 LLM 호출의 접합점

---

## 7. 모든 것은 파일이다 — 왜 파일 기반인가

**결정:** 설정, 스키마, 프로필, 규칙은 모두 파일로 관리한다.

**왜:**

- 파일은 git으로 추적된다. 변경 이력이 남는다
- 파일은 에이전트가 읽고 쓸 수 있다. GUI 설정은 에이전트가 접근할 수 없다
- 파일은 리뷰할 수 있다. 하드코딩된 상수는 찾기 어렵다
- `profiles/default.yaml`이 에이전트의 정체성과 약속을 정의한다. 코드가 아니라 선언이다

---

## 8. Execution 계층 구조화 — 왜 Repository/Domain Access/Services인가

**결정:** `src/execution/`을 `repository/`, `domain-access/`, `services/`로 나눈다.

**왜:**

- **Repository**는 DB를 추상화한다. 테스트에서 in-memory 구현으로 교체하면 DB 없이 전체 로직을 검증할 수 있다
- **Domain Access**는 Repository 위에 타입 검증 래퍼를 둔다. `findByIdForUser()`가 반환한 일반 Artifact를 `SoulProfileArtifact`로 단언하는 식이다. 이 계층이 없으면 feature 코드마다 타입 캐스팅이 흩어진다
- **Services**는 LLM, 외부 API 등 Repository와 독립적인 외부 연결을 담당한다

**soulmate에서 발견:** 템플릿에 이 골격이 없어서 프로젝트 초기에 직접 만들어야 했다. 두 번째 프로젝트에서도 같은 구조가 필요할 것이다.

---

## 9. Route Handler 헬퍼 — 왜 공통화하는가

**결정:** `src/lib/http/route-handler.ts`에 JSON 파싱, Zod 에러 포매팅을 모은다.

**왜:**

- 모든 Next.js API 라우트에서 `request.json()` 파싱과 Zod 검증 에러 처리가 반복된다
- 반복 코드를 각 라우트에 두면 에이전트가 조금씩 다른 방식으로 구현한다 — 일관성이 깨진다
- 공통 헬퍼로 모으면 에러 응답 형태가 통일되고, 라우트 핸들러는 비즈니스 로직에만 집중한다

---

## 10. Artifact 타입 확장 전략 — Discriminated Union

**결정:** Artifact 타입이 늘어나면 `ArtifactBase<TType, TMetadata>` 제네릭으로 확장하고, discriminated union으로 합친다.

**왜:**

- 새 타입을 추가할 때 TypeScript가 누락된 케이스를 컴파일 타임에 잡아준다
- Zod 스키마도 `z.discriminatedUnion("type", [...])`으로 일관되게 확장할 수 있다
- `type: "soul-profile"`과 `metadata: SoulProfileMetadata`의 쌍이 타입 레벨에서 보장된다 — 런타임 타입 단언의 부담이 줄어든다
